## Notes

### Validation iteration 1 — issues found and fixed

1. **Implementation leakage in requirements.** The first draft named the transformation tool and its command forms directly (`dbt run --select`, `--full-refresh`, `dbt seed`). Rewritten to "transformation command", "full-rebuild instruction", and "reference-data loading" so requirements state the outcome rather than the mechanism. The originating issue's concrete command tables are intentionally *not* reproduced in the spec; they belong in the plan.
2. **Success criteria were tool-specific.** `SC-003`/`SC-004` originally counted "dbt invocations". Retained as counts of "transformation commands" and "fixed startup overhead", which are measurable and meaningful without naming the tool. `SC-001` carries the user-facing wall-clock outcome.
3. **"Bit-for-bit" was imprecise.** `SC-002` claimed bit-for-bit identity while `FR-008` excludes timestamp columns. Reworded to "unchanged: zero differing rows … excluding timestamp columns" so the two agree.

### Deliberate deviations from the template

- **`Out of Scope` and `Assumptions` sections added.** The corrected empirical ceiling is about 10s, and the work does not touch SQL or orchestration optimization. Recording that prevents scope creep into separate efforts.
- **Story priority follows risk-adjusted value.** Story 2's corrected ceiling is only ~6–7s and it touches per-year simulation semantics — where Feature 121's Tier C failed — so the specification permits an explicit stop after Story 1.

### Validation iteration 2 — `/speckit.clarify` session 2026-08-02

Four questions asked and integrated. Two of them corrected defects in the spec that would have survived into planning:

1. **The parity gate was under-scoped (Q1).** `FR-006` originally named three tables, following the originating issue. Feature 121's existing contract (`specs/121-reduce-dbt-invocations/contracts/correctness-parity.md`) is an all-marts, duplicate-preserving, bidirectional comparison with a determinism re-run. Narrowing it would have weakened the exact gate that last caught this class of bug. Now reuses 121's contract verbatim (`FR-006`–`FR-009`, `FR-011`).
2. **The command-count target was arithmetically unreachable (Q3).** "20 → 12" required collapsing first-year setup from 6 commands to 2, which `FR-005` (never silently downgrade a full rebuild) forbids — rebuild instructions apply per command, not per model. Relaxed to 14, now explicitly derived from the rebuild floor rather than guessed.
3. **The headline time target punished the expected outcome (Q2).** A single 20s whole-feature bar meant that reverting Story 2 on parity grounds — the most likely outcome given Tier C's history — would mark the feature failed, creating pressure to keep a step that should be reverted. Replaced with per-step bars (`SC-001`, `SC-002`) and a feature-level completion condition (`SC-004`).
4. **Gate location settled (Q4).** Local pre-merge with committed evidence (`FR-013`), not CI: four full 60k runs per gate would distort CI shard balance for a check that runs twice in the feature's lifetime.

### Factual findings during clarification

- **No 60k census exists in the repository.** All three census parquet files are 7,505 rows; the 60,040 reference workload is generated by `scripts/perf_profile/make_large_census.py` at 8× scale. Recorded in Assumptions — the gate depends on that generation being reproducible and identical across both sides of an A/B.
- **Feature 121 already provides the parity contract and the measurement harness** (`scripts/perf_profile`), so `FR-006`–`FR-013` and `FR-017`–`FR-020` should reuse rather than rebuild.

### Open items for `/speckit.plan`

- The mechanism for collapsing the first-year setup while preserving per-model full-rebuild semantics remains the main design question. `FR-005` constrains the outcome without prescribing the approach; if planning finds a way to honor it with fewer rebuild groups, `SC-006` can tighten below 14.
- Whether the parity harness reuses Feature 121's tooling directly or needs adaptation is a planning decision; `FR-006`–`FR-013` specify only the gate's shape.

### Assumption accepted without a clarification round

- **Baseline dependency.** Resolved by specifying a self-baselined A/B (`FR-010`) rather than comparison against a recorded historical baseline. This removes the originating issue's stated dependency on the companion baseline issue (#520). If that dependency was meant to be load-bearing for some reason not stated in the issue, flag before `/speckit.plan`.
